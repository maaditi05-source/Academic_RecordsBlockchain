Registration & Requests Module — Documentation

Project Context

The Academic Records Blockchain system is built on Hyperledger Fabric 2.x for managing student academic records at NIT Warangal. The project is divided into four modules:

Module Scope
Registration & Requests ← (this document) User registration, student enrollment, certificate requests
Verification & Approval Multi-party approval chain for academic records
IPFS Storing & Fetching Off-chain document storage via IPFS
Distributed Peer / Connection Fabric network topology, peer gossip, channel config

1.2 Registration Data Flow

sequenceDiagram
    participant U as User (Browser)
    participant FE as Angular Frontend
    participant BE as Express Backend
    participant UM as UserManager (JSON)
    participant FCA as Fabric CA
    participant CC as Chaincode (Go)
    participant WS as World State

    U->>FE: Fill registration form
    FE->>BE: POST /api/auth/register
    BE->>UM: createUser() — hash password, write to users.json
    UM-->>BE: User record (id, role, dept)

    alt Role = student
        BE->>FCA: registerUser() — enroll X.509 identity
        FCA-->>BE: Wallet identity stored
        BE->>CC: submitTransaction("CreateStudent", ...)
        CC->>WS: PutState(rollNumber, studentJSON)
        CC->>WS: PutPrivateData(aadhaarHash, phone, personalEmail)
        CC->>WS: Create composite keys (dept, year, status, all)
        CC-->>BE: Success
        BE->>UM: createStudentUser() — auto-create auth account
    else Role = department / verifier
        BE->>FCA: registerUser() — enroll into role-specific CA
        FCA-->>BE: Wallet identity stored
    end

    BE-->>FE: 201 Created + JWT tokens
    FE-->>U: "Registration successful! Please login."

2. Observations from the Old Repo

2.1 Registration Subsystem

# Observation Details
O1 JSON flat-file as user database userManager.js reads/writes data/users.json for all auth operations. This is a single point of failure with no concurrency safety — simultaneous register calls can cause data loss.
O2 Password stored as bcrypt hash Using bcryptjs with 10 salt rounds. Adequate for a prototype but the password policy is minimal (≥ 6 chars only).
O3 Dual identity model Every user exists in two places: the JSON file (for login/JWT) and the Fabric CA wallet (for blockchain transactions). These can go out of sync if one operation succeeds and the other fails.
O4 Student registration is admin-only at chaincode level CreateStudent chaincode enforces NITWarangalMSP only. Students cannot self-register on-chain; the backend uses admin identity to create them.
O5 Private Data Collection for sensitive fields Aadhaar hash, phone, personal email are stored in a PDC — only NITWarangalMSP can read them. Good privacy design.
O6 Auto-seeding on startup server.js runs autoSeedBlockchain() on boot — idempotent re-creation of students, departments, and courses from JSON seed files. Clever for dev, but the seed data is hardcoded.
O7 Frontend registration form is limited The Angular RegisterComponent only allows "Department" and "Verifier" roles. There is no student self-registration on the frontend — students are created by admin through the admin dashboard.
O8 Refresh tokens stored in-memory refreshTokens = new Map() — lost on every server restart.
O9 Default password = roll number When admin creates a student, the default password is set to the roll number itself. This is insecure if students forget to change it.
O10 No email verification Registration accepts any email without verifying ownership.

2.2 Certificate Requests Subsystem

# Observation Details
O11 Certificate requests stored off-chain in JSON data/certificate-requests.json is used instead of the blockchain. Requests are not immutable and can be tampered with.
O12 No workflow state machine for requests The request status transitions (PENDING → APPROVED/REJECTED) have no enforcement — any admin/HOD can set any status.
O13 Certificate types mismatch between frontend and backend Frontend offers "TRANSFER" and "CONSOLIDATED_MARKSHEET" types, but the chaincode only validates: DEGREE, TRANSCRIPT, PROVISIONAL, BONAFIDE, MIGRATION, CHARACTER, STUDY_CONDUCT.
O14 No request tracking on blockchain Only the issued certificate (with PDF hash, IPFS CID) goes on-chain. The request lifecycle is entirely off-chain and cannot be audited.
O15 No duplicate request detection A student can submit unlimited duplicate requests for the same certificate type.

2.3 General Observations

# Observation Details
O16 Wallet sync on startup walletSync.js handles stale Fabric keys after network restarts — a good resilience mechanism.
O17 Event listener disabled The initializeEventListener() function is disabled due to "SDK compatibility issues". Real-time blockchain event push does not work.
O18 Socket.io notifications partially implemented The approval controller sends Socket.io events, but the registration/request module does not.

3. Enhancements — Proposed (Can Be Done)

# Enhancement Rationale Complexity
E1 Replace users.json with a proper database (SQLite / MongoDB) Eliminates race conditions, enables querying, supports concurrent access. Medium
E2 Store certificate requests on-chain Makes the request lifecycle immutable and auditable. Add a CertificateRequest struct to chaincode with status transitions enforced by smart contract logic. High
E3 Add email verification (OTP) Prevent fake registrations by requiring email ownership proof before activating the account. Medium
E4 Enforce first-login password change Track a mustChangePassword flag and block API access (except password change) until the student changes their default password. Low
E5 Add duplicate request detection Check existing pending/approved requests for the same student + certificate type before allowing a new submission. Low
E6 Align certificate types across frontend and chaincode Add TRANSFER and CONSOLIDATED_MARKSHEET to the chaincode validation, or remove them from the frontend. Low
E7 Persist refresh tokens to Redis/DB Prevent session loss on server restart. Medium
E8 Student self-registration flow Allow students to register themselves through the frontend with HOD/admin approval before blockchain enrollment. Medium
E9 Request status notification via Socket.io Push real-time updates to students when their certificate request status changes. Low
E10 Audit trail for request status changes Log who changed the status, when, and with what comment — either on-chain or in a persistent store. Medium

4. Enhancements — Already Implemented

Based on analysis of the codebase, these are enhancements already built into the system beyond a basic prototype:

4.1 Registration Enhancements

# Enhancement Implementation
✅ I1 Automatic Fabric CA enrollment on login authController.js: If a user logs in but lacks a Fabric wallet identity, the system auto-enrolls them on the fly. This self-heals after network restarts.
✅ I2 Multi-MSP role-based CA routing fabricCAClient.js: getCAClientForRole() routes enrollment to the correct CA — NITWarangal (admin/student), Departments (department), or Verifiers (verifier).
✅ I3 Private Data Collection for student PII chaincode.go: Sensitive data (Aadhaar hash, phone, personal email) is stored in a Fabric Private Data Collection, not on the public ledger. Only NITWarangalMSP can access it.
✅ I4 Composite key indexing for efficient queries chaincode.go: Four composite keys created per student for O(1) lookups by department, enrollment year, status, and a global list.
✅ I5 Automatic auth account creation for students studentController.js: When admin creates a student on the blockchain, a login account is automatically generated in users.json with a default password.
✅ I6 Idempotent auto-seeding server.js: On backend startup, missing students/departments/courses are re-created on the blockchain. The check-then-create pattern is idempotent — safe for unlimited restarts.
✅ I7 Wallet stale-key auto-recovery walletSync.js: Detects and replaces stale cryptographic keys in the wallet after Fabric network restarts.
✅ I8 Comprehensive input validation at chaincode level chaincode.go: Validates email format (@student.nitw.ac.in domain), roll number length, name length, enrollment year range, grade values, credit ranges, and semester bounds — all enforced at the smart contract layer.
✅ I9 Blockchain event emission chaincode.go: StudentCreated, StudentStatusChanged, StudentDepartmentChanged events are emitted on-chain for potential listeners.
✅ I10 JWT refresh token system authController.js: Access + refresh token architecture for session management.

4.2 Certificate Request Enhancements

# Enhancement Implementation
✅ I11 Role-based request filtering certificateController.js: Students see only their own requests; admin/faculty see all.
✅ I12 Multiple certificate types supported certificate-request-dialog.component.ts: Degree, Transcript, Bonafide, Provisional, Transfer, Migration, Consolidated Marksheet.
✅ I13 Purpose categorization certificate-request-dialog.component.ts: Employment, Higher Studies, Visa, Loan, Other — enables analytics on request reasons.
✅ I14 Multi-party approval chain for academic records approvalController.js: Six-step workflow: DRAFT → SUBMITTED → FACULTY_APPROVED → HOD_APPROVED → EXAM_LOCKED → DEAN_APPROVED → FINALIZED. Each step is a separate API endpoint with role checks.
✅ I15 Modern, responsive UI with Material Design register.component.ts: Animated backgrounds, glassmorphism cards, password strength indicator, role selection cards, mobile-responsive layout.
